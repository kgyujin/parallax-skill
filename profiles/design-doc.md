# 프로파일: design-doc

설계 문서 · 구현 계획 · RFC · ADR · 기술 제안서. **구현 전** 검증이 핵심 가치다.

## 이 프로파일이 존재하는 이유

계획 단계의 결함은 고치는 데 한 문단이 들지만, 구현 후에 발견하면 한 주가 든다.
그런데 계획을 세운 모델은 그 계획의 가정을 의심하지 못한다 — 자기가 만든 가정이기 때문이다.

## 결함의 정의

**이 계획대로 진행했을 때 실패하거나, 되돌리기 어려워지거나, 다시 논의하게 되는 지점.**

문서가 못생긴 것은 결함이 아니다. 문서대로 했을 때 터지는 것이 결함이다.

## 검증 대상 수집

문서 경로와 함께 **문서가 다루는 실제 코드/시스템 경로**도 준다.
문서만 읽으면 "현재 코드가 이미 그렇게 돼 있다"거나 "그 모듈은 그렇게 동작하지 않는다"를 잡을 수 없다.

```
설계 문서:  ./docs/adr-007-caching.md
관련 코드:  ./src/cache/, ./src/api/handlers.py
기존 제약:  ./AGENTS.md
```

## 증거 형식 (필수)

```
문서 인용: "<해당 섹션 또는 문장 그대로>"
시나리오: <이 가정이 깨지는 구체적 상황>
결과:     <그때 무슨 일이 벌어지는가>
```

"확장성 고려가 부족하다" — 증거 아님.
"3절은 캐시 키를 user_id로 잡는데, 5절의 다중 테넌트 요구사항에서는 같은 user_id가 테넌트별로 다른 데이터를 가리킨다. 테넌트 A의 응답이 테넌트 B에 노출된다" — 증거.

## 카테고리

| 카테고리 | 내용 |
| --- | --- |
| `missing_requirement` | 다뤄야 할 요구사항이 문서에 없다 |
| `wrong_assumption` | 문서가 참으로 두는 전제가 실제로는 거짓이다 |
| `internal_contradiction` | 문서 안의 두 부분이 서로 모순된다 |
| `unhandled_failure` | 실패·부분실패·타임아웃 경로가 정의되지 않았다 |
| `no_rollback` | 되돌리는 방법이 없거나, 되돌리면 데이터가 깨진다 |
| `contract_break` | 기존 API·스키마·이벤트 계약을 깨는데 마이그레이션 경로가 없다 |
| `simpler_alternative` | 같은 목표를 훨씬 단순하게 달성하는 방법이 있다 (**구체적 대안 제시 필수**) |
| `unverifiable` | 성공 기준이 검증 가능한 형태가 아니다 ("잘 동작하게 만든다") |
| `scope_creep` | 해결하려는 문제에 비해 범위가 과도하다 |

## 심각도

- `critical` — 이 상태로 구현하면 데이터 손상·보안 문제·되돌릴 수 없는 마이그레이션이 발생한다.
- `major` — 구현 도중 막히거나, 완성 후 다시 설계해야 한다.
- `minor` — 문서를 읽는 사람이 오해할 수 있다. 구현은 진행 가능하다.

## 지적 금지

- 문서 형식·템플릿 준수 여부 (요청받은 경우 제외)
- 이미 "범위 밖(out of scope)"으로 명시된 항목
- 대안 없는 반대 — `simpler_alternative`는 **구체적으로 무엇을 어떻게** 하자는 게 없으면 폐기
- 취향 수준의 기술 선택 논쟁 (실패 시나리오를 제시할 수 없다면)
- 문서에 없는 미래 요구사항 상상 ("나중에 X가 필요해지면")

## 브리프 추가 항목

- 이 설계가 **이미 결정된 제약**과 **아직 열린 선택지** 중 어디에 속하는지
  (이미 사용자가 결정한 사안을 재논의하는 findings를 막는다)
- 문서의 대상 독자와 목적 (합의용인지, 기록용인지, 구현 지침인지)
